# ПОСТОЯННАЯ ПАМЯТЬ ПРОЕКТА И ПОРЯДОК ПЕРЕДАЧИ РАБОТЫ

Организуй знания так, чтобы новый агент после потери истории чата
мог найти правила, запустить проект, понять состояние работы
и продолжить без повторения прежних ошибок.

Не ограничивайся обещанием «запомнить».
Создай или обнови файлы, сохрани их в Git и проверь удалённую копию.

## 1. СНАЧАЛА ИЗУЧИ СУЩЕСТВУЮЩУЮ СТРУКТУРУ

Прочитай AGENTS.md, README и существующую документацию.
Если подходящая система памяти уже существует — развивай её.
Не создавай параллельные документы с противоречащими правилами.

Сохрани существующие пользовательские изменения.

## 2. ОДНА ПОНЯТНАЯ ТОЧКА ВХОДА

В корневом AGENTS.md добавь короткую инструкцию:

«Перед работой прочитай индекс знаний проекта, текущий статус
и стандарт затрагиваемой системы. После существенных изменений
обнови соответствующие записи и сохрани их в удалённом Git».

Добавь реальные ссылки на файлы.

Если структуры ещё нет, используй:

docs/project-memory/README.md
docs/project-memory/CURRENT.md
docs/project-memory/ROADMAP.md
docs/project-memory/DECISIONS.md
docs/project-memory/standards/
docs/project-memory/recovery.md

Назначение:
- README — карта документации и порядок чтения.
- CURRENT — актуальное состояние и следующий конкретный шаг.
- ROADMAP — очередь задач с критериями завершения.
- DECISIONS — важные решения, причины и отвергнутые подходы.
- standards — устройство и правила отдельных систем.
- recovery — запуск, восстановление, проверки и публикация.

AGENTS.md сохраняй компактной точкой входа.
Подробные объяснения размещай в тематических документах.

## 3. ЧТО ДОЛЖЕН ПРОЧИТАТЬ НОВЫЙ АГЕНТ

В начале каждой новой сессии:

1. AGENTS.md.
2. Индекс README.
3. CURRENT и актуальные задачи ROADMAP.
4. Стандарт изменяемой системы.
5. Нужные решения и QA-доказательства.

Затем проверить настоящий checkout:
ветку, SHA, локальные изменения и состояние удалённой ветки.

Документация описывает ожидаемое состояние.
При расхождении с кодом сначала выясни причину.
Не уничтожай изменения, чтобы формально привести всё к записи.

## 4. ФОРМАТ CURRENT.md

Держи его коротким и актуальным:

- Дата обновления.
- Рабочая ветка и SHA базы.
- Последняя подтверждённая публикация и ссылка.
- Активная задача.
- Уже сделанные изменения.
- Незавершённые части.
- Завершённые проверки и их результат.
- Текущий блокер, если есть.
- Следующий конкретный шаг.
- Где находится сохранённый WIP.
- Ссылки на относящиеся стандарты и доказательства.

Различай состояния:
запланировано / реализуется / реализовано локально /
проверено / опубликовано / одобрено пользователем / отклонено.

Не помечай задачу завершённой по одному успешному тесту.

## 5. КАК ЗАПИСЫВАТЬ ЗНАНИЯ О СИСТЕМЕ

Для воды, грунта, ТРЦ, управления, сохранений и других систем
создавай отдельный стандарт.

Каждая запись содержит:

### Требование
Что именно хочет пользователь.
Какие последние уточнения заменили прежние требования.

### Источники истины
Полные SHA, настоящие файлы, изображения и ссылки.
Отдельно обозначай:
исторический исходник, контрольную версию,
целевой референс и текущую опубликованную реализацию.

### Устройство
Точки входа, зависимости, форматы данных,
владельцы ресурсов и важные ограничения.

### Воспроизведение
Точные команды, версии инструментов, параметры,
seed, входные ресурсы и ожидаемый результат.

### Проверки
Как доказать правильность поведения, сохранений,
внешнего вида и производительности.

### Известные ошибки
Симптом → установленная причина → исправление →
проверка, предотвращающая повторение.

Предположения помечай как предположения.
Не записывай их в раздел установленных причин.

## 6. ОСОБОЕ ПРАВИЛО ДЛЯ ТЕКСТУР И ВИЗУАЛЬНЫХ РЕШЕНИЙ

Сохраняй:
- Оригинальный источник и лицензию.
- Имена файлов и контрольные суммы.
- Исходные и преобразованные ресурсы либо способ их получения.
- Скрипт обработки.
- Версии инструментов, параметры и seed.
- Размеры, упаковку каналов и цветовые пространства.
- Масштаб в мире и настройки материала.
- Стоимость по памяти и отрисовке.
- Эталонные кадры и условия их получения.

Знание «взяли красивую текстуру» недостаточно.
Следующий агент должен суметь получить тот же результат.

Для воды отдельно опиши генерацию полей, отражений,
настройки глубины, прозрачности, ряби и бликов.

## 7. НЕ ТЕРЯЙ УТОЧНЕНИЯ ИЗ ЭТОГО ЧАТА

При актуализации правил учти последнее известное:

- Ходьба и плавание за Чичи — от третьего лица.
  Это заменило прежнее требование первого лица.
- Камера случайного посетителя ТРЦ — близкая,
  без чрезмерного взгляда сверху.
- Обзор этажа сверху — отдельный режим.
- Вода горок и d6fa805 — исторические исходники/контроль.
- Crimson Desert — выбранный пользователем целевой
  визуальный ориентир воды.
- Исторический коммит не является потолком качества.
- Новый материал или успешная компиляция шейдера
  не означают визуального одобрения.
- Средний FPS не исключает длинные фризы.

Сверь эти записи с последующими указаниями пользователя.
При изменении требования обновляй старый противоречащий пункт,
сохраняя причину изменения в DECISIONS.

## 8. QA ДОЛЖНО СООТВЕТСТВОВАТЬ ТОЧНОЙ СБОРКЕ

Используй существующую QA-структуру либо:

docs/qa/YYYY-MM-DD/название-этапа/

Рядом с результатами сохраняй manifest:

- SHA исходников.
- Наличие незакоммиченных изменений.
- Точный идентификатор снимка WIP, если изменения были.
- Идентификатор проверенной сборки и asset hashes.
- Версии Node, браузера и параметры запуска.
- Тестовое сохранение/seed.
- Локацию, камеру, игровое время, DPR и качество.
- Команды и результат завершения.
- Passed/failed/interrupted/skipped.
- Кадры, замеры и нужные журналы.

Нельзя приписывать PNG одной сборки более позднему исходнику.

Последние строки журнала не доказывают успешного завершения
процесса. Сохраняй настоящий итог и код завершения.

Для визуальных изменений:
одинаковые кадры ДО/ПОСЛЕ и проверка движения.

Для оптимизации:
одинаковое качество, мир и сценарий;
полное время кадра, длинные паузы и память.

## 9. СОХРАНЯЙ НЕУДАЧНЫЕ ПОДХОДЫ

В DECISIONS записывай существенные ошибки:

- Что пытались сделать.
- Почему подход выбрали.
- Что фактически произошло.
- Как установили причину.
- Что сохранили, исправили или отклонили.
- Как не повторить ошибку.

Отклонённый материал не должен позже снова появиться
как «новое улучшение» из-за потери контекста.

Не сохраняй каждую команду подряд.
Сохраняй выводы, необходимые для продолжения.

## 10. GITHUB — ОБЯЗАТЕЛЬНАЯ УДАЛЁННАЯ КОПИЯ

Файл только в /workspace может исчезнуть вместе со средой.

Документацию коммить вместе с соответствующим этапом.
После push проверь существование точного коммита на сервере.

Для длительной незавершённой работы используй удалённую
WIP-ветку с понятным назначением.
Сначала проверь workflow: WIP не должна случайно
опубликоваться на боевом сайте.

Не сбрасывай текущие правки ради создания копии.
Добавляй файлы в коммит осознанно.

Не включай секреты, .env, credential files
и живые пользовательские базы.

## 11. РЕЗЕРВНАЯ КОПИЯ ДЛЯ ВОССТАНОВЛЕНИЯ

Перед рискованными операциями и сменой среды сохраняй:

- SHA базы.
- Нужные локальные коммиты и Git-ссылки.
- Изменённые и новые файлы.
- Удаления.
- git diff HEAD --binary.
- git diff --cached --binary.
- Статус Git.
- Инструкцию восстановления.
- Необходимые внешние ресурсы или способ их получения.

Git bundle сам по себе не сохраняет незакоммиченные файлы.
Архив рабочих файлов сам по себе не сохраняет всю Git-историю.

Для linked worktrees учитывай общий Git-каталог
и состояние каждого рабочего дерева.

Если используется Git LFS, проверь доступность самих объектов,
а не только текстовых указателей.

Проверь архив и пробное восстановление.
Сохрани независимую копию вне этой рабочей машины.

Локальная ссылка /workspace — не независимая резервная копия.
Временные GitHub Actions artifacts — не единственное
долговременное хранилище.

## 12. ОБНОВЛЯЙ ПАМЯТЬ ПО ХОДУ РАБОТЫ

Обновляй записи после:
- Важного уточнения пользователя.
- Существенного открытия.
- Обнаруженной причины ошибки.
- Законченного этапа реализации.
- Завершённой проверки.
- Публикации.
- Отклонения результата пользователем.
- Передачи работы следующему агенту.

Не откладывай всё документирование до конца большой задачи.

## 13. КРИТЕРИЙ ГОТОВНОСТИ ПЕРЕДАЧИ

Другой агент из свежего checkout должен суметь:

1. Найти правила через AGENTS.md.
2. Понять текущую задачу и следующий шаг.
3. Найти код, эталоны и исходные материалы.
4. Запустить нужные проверки.
5. Отличить опубликованное от WIP.
6. Найти известные ошибки.
7. Восстановить незавершённую работу из сохранённой копии.

В отчёте дай настоящие проверенные ссылки:
- На индекс знаний.
- На CURRENT.
- На стандарт изменённой системы.
- На сохранённую ветку/коммит.
- На резервную копию, когда она создавалась.

Не сообщай «всё сохранено», пока удалённая копия
и ссылки фактически не проверены.
